# Database plan

One PostgreSQL database (`perfumeshop`), **one schema per module**. This document is the
data model. Every module schema is implemented: `catalog`, `customers` + `identity`, `inventory`, `orders`,
`shipping`, `payments`, `notifications` and `administration` (plus `hangfire`, owned by the job library).

## Conventions (all modules)

| Topic | Rule |
|---|---|
| Naming | `snake_case` tables and columns, plural table names (`fragrance_variants`). |
| Primary keys | `id uuid`, generated by the application (UUID v7, time-ordered for index locality). |
| Timestamps | `created_at_utc` / `updated_at_utc` as `timestamptz`, set by a SaveChanges interceptor. |
| Money | Two columns: `<name>_amount numeric(10,2)` + `<name>_currency char(3)`. All prices are EUR, VAT (18%) included. |
| Enums | Stored as `text` (readable, safe to reorder). Flag sets (seasons, occasions) as `integer` bit flags. |
| JSON | Value objects that are always read with their owner (notes, accords, images, raw API payloads) are `jsonb`. |
| Concurrency | PostgreSQL `xmin` system column as optimistic concurrency token on aggregates edited by admins. |
| Foreign keys | **Only inside a schema.** A column pointing at another module (e.g. `orders.order_lines.variant_id`) is a plain `uuid` with no FK ("soft reference"), plus a snapshot of the data needed (name, price, …). |
| Migrations | Each module has its own migrations and its own history table: `<schema>."__EFMigrationsHistory"`. |
| Outbox | Every module that publishes integration events has `<schema>.outbox_messages` (see bottom). |

Ownership legend: each table below is written **only** by its module. Other modules read it
through the owning module's `.Contracts` API or keep their own copy updated by events.

## customers + identity (implemented)

Customer profiles, verified phone numbers, saved addresses and OTP codes in schema **`customers`**;
ASP.NET Identity and refresh tokens in schema **`identity`**. Both are owned by the Customers module
and mapped by **one** DbContext (`CustomersDbContext`, migrations history in `customers`), so the
first OTP login creates the customer and its login account in a single transaction, and
`identity.users.customer_id` can be a real foreign key.

| Column | Type | Notes |
|---|---|---|

(lockout after 5 failures; TOTP 2FA, required for Admin by default). The first Admin comes from `Auth:SeedAdmin` (user-secrets / env vars).
Access tokens are JWTs (15 minutes) with `sub`, `role` and, for customers, `customer_id`; staff tokens also carry
`email` and `mfa=true` when signed in with 2FA.

## orders (implemented)

Cash on Delivery orders. Status machine (rules inside the `Order` aggregate):
Pending → Confirmed → Shipped → Delivered → CashCollected; Pending (customer or staff) / Confirmed (staff) →
Cancelled; Shipped → Refused; Pending → Expired (not confirmed within `order_settings.pending_expiry_hours`).
Amounts are `numeric(10,2)` in the order's `currency` (EUR), **VAT included**; the 18% VAT part is stored separately.

## inventory (implemented)

Stock per Catalog variant, goods receipts with batch codes and supplier invoices (proof of
authenticity), reservations per order line and an append-only ledger. Catalog shows an "in stock"
flag through `IInventoryApi`; it stores no stock itself.

### `inventory.stock_items` (aggregate root)
| Column | Type | Notes |
|---|---|---|
| `variant_id` | uuid | PK = Catalog variant id (**soft reference**, no FK) |
| `on_hand` | integer | units in the warehouse; always = sum of batch remainders |
| `reserved` | integer | held for order lines not shipped yet |
| `low_stock_threshold` | integer | per variant; new items get `Inventory:DefaultLowStockThreshold` (3) |
| `created_at_utc`, `updated_at_utc` | timestamptz | |
| `xmin` | xid | **optimistic concurrency**: every stock change updates this row; the loser of a race is retried with fresh numbers |

Checks: `on_hand >= 0`, `0 <= reserved <= on_hand` (so available = on_hand − reserved is never negative), `low_stock_threshold >= 0`.

## shipping (implemented)

Couriers, parcels and Cash on Delivery settlement. No courier has an API: everything is manual or CSV through
`ICourierAdapter` (`ManualCourierAdapter`). Shipping owns courier + tracking and drives the order through
`IOrdersApi` (Orders never references Shipping; an architecture test enforces it).

Status machine: Created → HandedOver → InTransit → Delivered / Refused → ReturnedToWarehouse (Delivered/Refused also
directly from HandedOver). Order effects: Created → order Shipped (stock committed), Delivered → order Delivered,
ReturnedToWarehouse → order Refused (stock back into its batches), settlement → order CashCollected.
A courier-reported Refused does **not** touch the order or stock: the parcel is still on its way back.

**Fiscal receipt check at handover.** A failed or missing receipt never blocks creating the shipment. But
Created → HandedOver (manifest handover, single parcel, or a courier status file) needs the order's sale receipt
to be `Issued` (`IPaymentsApi.GetSaleReceiptsAsync`). Otherwise: 409 `Shipping.Shipment.ReceiptMissing` listing
the parcels (manifest handover is all-or-nothing), or `overrideMissingReceipt: true` + reason (5-500 chars).
Courier files cannot override (line outcome `ReceiptMissing`). The manifest (HTML and CSV) has a "Kupon fiskal"
column (`OK` / `PA KUPON (Failed|Pending|Missing)`) and a warning banner when any parcel has no issued receipt.

### `shipping.shipment_status_changes` (timeline)
`id`, `shipment_id` (FK cascade), `from_status`, `to_status`, `actor_id` (staff user id), `source` (`Manual`, `CsvImport`,
`Settlement`), `note`, `changed_at_utc`.

### `shipping.status_imports` (courier status files)
`id`, `courier_id` (FK), `file_hash` (SHA-256 of the normalized content), `imported_by`, `imported_at_utc`, `results` jsonb
(per line: Applied / AlreadyApplied / UnknownTracking / InvalidStatus / InvalidTransition / OrderUpdateFailed).
**Unique (`courier_id`, `file_hash`)**: the same file again returns the stored result. Repeated or late updates inside
different files are "AlreadyApplied".

### `shipping.settlements` + `shipping.settlement_lines` (COD remittance statements)
| Table | Columns | Notes |
|---|---|---|
| `settlements` | `id`, `courier_id` (FK), `courier_name`, `reference`, `file_hash`, `imported_by`, `imported_at_utc` | **unique (`courier_id`, `file_hash`)**: re-importing a file returns the same settlement |
| `settlement_lines` | `id`, `settlement_id` (FK cascade), `line_number`, `tracking_number`, `collected_amount`, `fee`, `status`, `shipment_id`, `order_number`, `expected_amount`, `expected_fee`, `note` | status: `Matched`, `AmountMismatch`, `UnknownTracking`, `AlreadySettled`, `NotPayable`, `DuplicateInFile`, `OrderUpdateFailed` |

Only `Matched` lines (exact amount, delivered or in transit, not settled before) book money: the shipment gets
`settlement_id` and the order becomes CashCollected. A parcel can be settled once (`shipments.settlement_id`).
"Delivered but not paid after `remittance_days`" is computed from `shipments` for the reports.

### `shipping.outbox_messages`
Same shape as Orders; Hangfire job `shipping-outbox`. Events: `ShipmentCreated`, `ShipmentHandedOver`, `ShipmentDelivered`, `ShipmentRefused`, `CodSettled`.

## payments (implemented)

Cash on Delivery only (`IPaymentProvider` → `CashOnDeliveryProvider`). One payment record per order and the
fiscal receipts. Payments never changes Orders or Shipping: it only reacts to their integration events
(through their outboxes), each handled once per event id (`payments.inbox_messages`).

| Event | Effect |
|---|---|
| `OrderPlaced` | payment `Expected` (amount = order total) |
| `OrderShipped` | courier + tracking on the payment; **sale receipt** created and issued |
| `OrderCashCollected` | payment `Collected` (amount) |
| `CodSettled` (Shipping) | per statement line: collected, courier fee, net = collected − fee, link to the settlement |
| `OrderRefused` (parcel back in the warehouse) | payment `Failed`; **storno** of the issued sale (or the sale is `Voided` if it was never issued) |
| `OrderCancelled`, `OrderExpired` | payment `Cancelled` |

If an event arrives before `OrderPlaced` was handled, the payment is created from `IOrdersApi` first.

### `payments.payments` (aggregate root, one per order)
| Column | Notes |
|---|---|
| `id`, `order_id` (soft), `order_number`, `customer_id` (soft) | **unique** `order_id` |
| `method` | `CashOnDelivery` (card gateways later = new value, no redesign) |
| `status` | `Expected` → `Collected` / `Failed` (refused) / `Cancelled` |
| `expected_amount`, `collected_amount`, `courier_fee`, `net_received` | numeric(10,2), EUR, VAT incl.; check constraint: no negatives |
| `courier_name`, `tracking_number`, `shipped_at_utc` | snapshot from `OrderShipped` |
| `collected_at_utc`, `settlement_id` (soft → `shipping.settlements`), `settlement_reference`, `settled_at_utc` | |
| `placed_at_utc`, `updated_at_utc`, `xmin` | indexes (`status`, `placed_at_utc`), `shipped_at_utc`, `collected_at_utc`, `settlement_id` |

### `payments.fiscal_receipts`
| Column | Notes |
|---|---|
| `id`, `internal_number` | our own number `PS-R-<year>-<000001>`, **unique**, never reused |
| `kind` | `Sale` or `Storno`; **unique** (`order_id`, `kind`): one sale and at most one storno per order |
| `order_id` (soft), `order_number`, `original_receipt_id`, `original_internal_number` | storno points to its sale |
| `status` | `Pending` → `Issued` / `Failed` (retry) / `Voided` (sale never issued, parcel refused) |
| `lines` jsonb | description, SKU, quantity, unit price, line total, VAT rate, VAT amount, batch codes; delivery fee is a line ("Transporti") |
| `vat_breakdown` jsonb | per rate: net, VAT, gross |
| `total`, `vat_total`, `currency`, `payment_method` | storno = exact negative of the sale |
| `provider`, `fiscal_number`, `is_fiscal` | development provider: `NONFISCAL-<internal number>`, `is_fiscal = false` |
| `created_at_utc`, `issued_at_utc`, `last_error`, `void_reason` | index (`status`, `created_at_utc`) for the failed list |

VAT: prices include 18 %. Per line `vat = round(gross × 18 / 118, 2, half away from zero)`, summed per rate
(same rounding as Orders, so receipt VAT = order VAT).

### `payments.fiscal_receipt_attempts` (audit, append-only)
`id`, `receipt_id`, `attempted_at_utc`, `provider`, `succeeded`, `request_json` jsonb (exactly what was sent),
`response_json` jsonb (raw answer), `error`. Every try is stored, also failed ones.

### `payments.receipt_number_counters`
`year` (PK), `last_number`. Incremented in the same transaction as the receipt (row lock), so numbers are gap-free per year.

### `payments.outbox_messages`
Same shape as Orders; Hangfire job `payments-outbox`. Event: `FiscalReceiptFailed` (one per failed attempt) → staff alert in Notifications.

### `payments.inbox_messages`
`event_id`, `consumer` (PK both), `processed_on_utc`. Written in the same transaction as the handler's changes.

### Fiscal provider
`IFiscalReceiptService` hides the real fiscal device / certified software / tax-authority API, which is
**not chosen yet** (docs/before-production.md). In Development `DevelopmentFiscalReceiptService` stores
NON-FISCAL receipts (printed with a "JO FISKAL – NON-FISCAL" banner); in every other environment
`UnconfiguredFiscalReceiptService` fails every issue (logged as an error, receipt `Failed`, visible in the
daily summary) until a real provider is implemented. Failed receipts are retried with
`POST /api/admin/payments/receipts/{id}/retry`.

## notifications (implemented)

Customer SMS (Albanian) and staff alert emails. Messages are queued from events (inbox, once per event) and
daily jobs, then sent by Hangfire job `notifications-dispatch` (every 30 s, `FOR UPDATE SKIP LOCKED`).
OTP codes do **not** go through this queue: Customers sends them directly with `ISmsSender` (no quiet hours, and
codes are never stored in the log).

| Trigger | Message |
|---|---|
| `OrderPlaced` | SMS `order-placed` (number, total, "do t'ju telefonojmë për konfirmim") + staff email `staff-new-order` |
| `OrderConfirmed` | SMS `order-confirmed` |
| `ShipmentHandedOver` (Shipping: the courier picked the parcel up) | SMS `shipment-handed-over` (courier, tracking number, COD amount). Booking the shipment (`ShipmentCreated`) sends nothing. |
| `ShipmentDelivered` (Shipping) | SMS `shipment-delivered` (thank you) |
| `OrderCancelled`, `OrderExpired` | SMS `order-cancelled`, `order-expired` |
| `OrderRefused`, `ShipmentRefused` | **nothing** (no SMS on refused parcels) |
| `FiscalReceiptFailed` (Payments) | staff email `staff-receipt-failed` |
| Hangfire job ends Failed (`IJobFailureListener`) | staff email `staff-job-failed` (once per job id) |
| outbox message fails for the last time (`IDeadLetterListener`) | staff email `staff-dead-letter` (once per message) |
| daily `notifications-low-stock` (08:00 Europe/Belgrade) | staff email `staff-low-stock` (variants at/below their threshold; once per day) |
| daily `notifications-unpaid-cod` (08:05 Europe/Belgrade) | staff email `staff-unpaid-deliveries` (delivered, not paid past the courier's remittance days; once per day) |

### `notifications.templates`
| Column | Notes |
|---|---|
| `key` (PK) | e.g. `order-placed`; the set of keys and their allowed placeholders is defined in code (`TemplateCatalog`) |
| `channel`, `audience` | `Sms`/`Email`, `Customer`/`Staff` |
| `subject` (email), `body` | Albanian; `{{placeholder}}` syntax, unknown placeholders rejected on save; SMS max 480, email 4000 |
| `transliterate` | SMS: ë→e, ç→c before sending, so the text stays GSM-7 (160 chars/SMS instead of 70) |
| `is_enabled`, `updated_by`, `created_at_utc`, `updated_at_utc`, `xmin` | |

Seeded on startup when a key is missing; edited templates are never overwritten.

### `notifications.messages` (the notification log)
| Column | Notes |
|---|---|
| `id`, `channel`, `audience`, `recipient` (E.164 phone or email), `template_key`, `subject`, `body` | `body` = exactly what was sent (rendered + transliterated) |
| `dedup_key` | **unique** `template:source:recipient` → each event / daily run produces each message at most once |
| `source_id`, `order_number` | event id, `low-stock-2026-11-26`, `job-1234`, ... |
| `encoding`, `segments` | SMS: `GSM-7`/`UCS-2` and billed segments (warning logged when > 1) |
| `status` | `Queued` → `Sent` / `Failed` |
| `send_after_utc`, `held_for_quiet_hours` | customer SMS queued 22:00-08:00 (Europe/Belgrade) wait until 08:00 |
| `next_attempt_at_utc`, `attempts` | retries after 1 min, 5 min, 30 min, 2 h; the 5th failure is final. A retry never lands in quiet hours |
| `provider`, `provider_message_id`, `last_error`, `sent_at_utc`, `resent_by` | staff can resend `Failed` messages |
| `created_at_utc`, `updated_at_utc`, `xmin` | indexes (`status`, `next_attempt_at_utc`), `created_at_utc`, `order_number`, `recipient` |

`id`, `message_id` → messages (cascade), `attempted_at_utc`, `provider`, `succeeded`, `provider_message_id`,

## Decisions log

1. **Stock** lives in Inventory, not Catalog.
2. **Identity** tables are owned by Customers, in schema `identity`, mapped by the same DbContext as `customers`. Roles: Admin, Staff, Customer.
3. **Fiscal receipt** is issued at shipment; a refused parcel gets a storno receipt. Behind `IFiscalReceiptService`.
4. **Bakhoor / non-liquid products:** variant size is `size_value` + `size_unit` (`Ml`, `Gram`, `Piece`).
5. **Refused parcels** go back into stock through `IInventoryApi.ReleaseAsync` on the committed line (status `Returned`, units back into the same batches).
6. **COD settlement** (courier remittance statements) lives in Shipping (`shipping.settlements`), next to the tracking numbers it matches on; Payments keeps the per-order payment record and fiscal receipts.
7. **Refused parcels: stock returns on ReturnedToWarehouse**, not when the courier reports the refusal, so units still in the courier's van are never sold twice. The order becomes Refused (storno trigger) at that moment too.
8. **Payments only listens.** All state changes come from Orders/Shipping events through the outbox (at-least-once) and are applied once per event (`payments.inbox_messages`). Expired orders are treated like cancelled ones.
9. **A failing fiscal provider never blocks shipping.** The receipt is stored as `Failed` with the attempt, logged as an error and retried by staff; outside Development there is no provider yet, so every receipt fails loudly.
10. **Courier fees** are recorded per order from the courier statement (`CodSettled` lines); net received = collected − fee.
11. **No parcel leaves without an issued fiscal receipt** unless staff override with a reason (stored on the shipment, in its timeline, and logged as a warning). Creating the shipment is never blocked.
12. **Notifications render at queue time.** The log stores the exact text sent; editing a template affects only new messages. Each message has a unique dedup key (template + source + recipient).
13. **Quiet hours (22:00-08:00 Kosovo time) apply to customer SMS only.** Staff emails go out at once; OTP codes bypass the queue entirely.
14. **SMS cost:** customer SMS are transliterated by default (ë→e, ç→c) so they stay one GSM-7 segment; the template list shows the segment count with and without transliteration.
15. **Business details live in the database** (`administration.business_profile`), not in configuration, so the owner can correct them without a deploy; configuration only seeds the first row.
16. **Audit log is one table for all modules** (`administration.audit_entries`), written through `IAuditLog` from any module, read only by Admin. It never blocks the action it records.
17. **Admins must use 2FA** (`Auth:Staff:RequireTwoFactorForAdmins`, default true): enforced by the Admin policy through the token's `mfa` claim, so it holds for every admin endpoint, not only the UI.
